# 1. Executive Summary

## 1.1 Product Vision

Build an engaging, affordable, mobile-first learning platform that helps Indian students, job seekers and early-career professionals develop useful life and career skills through short daily lessons, interactive exercises, audio content and gamified learning.

The application will take inspiration from the bite-sized learning experience of SmartyMe while differentiating itself through Indian contexts, accessible pricing, bilingual explanations and practical outcomes.

Users should be able to learn something useful in 5–15 minutes a day without needing to enroll in a lengthy course.

## 1.2 Problem Statement

Many learners face the following problems:

- Traditional courses require significant time and sustained commitment.
- Educational content is often too theoretical or disconnected from daily situations.
- Learners who understand Hindi may struggle with English-only learning resources.
- Many learning applications emphasize video consumption rather than active practice.
- Users find it difficult to build consistent learning habits.
- Career-oriented learners need practical communication and workplace skills but may not be able to afford expensive coaching.

## 1.3 Proposed Solution

The application will provide:

1. Short, structured daily lessons.
2. English communication and career learning paths.
3. Hindi/Hinglish explanations for accessible learning.
4. Interactive quizzes and scenario-based practice.
5. Audio narration for selected lessons.
6. Daily goals, XP, streaks and achievements.
7. Personalized lesson recommendations.
8. Free and premium learning access.
9. A content administration system for publishing and maintaining lessons.

## 1.4 Product Principles

- Mobile-first and Android-first.
- Learning outcomes before visual effects.
- Short lessons with meaningful practice.
- Low-bandwidth and budget-conscious implementation.
- Reusable content and animation assets.
- Clear, accessible language.
- Gamification that supports learning rather than distracting from it.
- Privacy, security and transparent monetization.

# 2. Product Goals and Non-Goals

## 2.1 Business Goals

- Validate demand for an Indian microlearning application.
- Acquire an initial cohort of active learners.
- Establish daily and weekly learning habits.
- Identify the most engaging learning categories.
- Validate willingness to pay for premium content.
- Build a scalable foundation for future courses and interactive learning experiences.

## 2.2 User Goals

Users should be able to:

- Discover relevant learning paths.
- Complete a useful lesson in 5–15 minutes.
- Practice what they have learned.
- Understand mistakes and receive explanations.
- Track their progress over time.
- Learn using English with optional Hindi/Hinglish support.
- Continue learning consistently without feeling overwhelmed.

## 2.3 MVP Non-Goals

The following are explicitly excluded from the initial release:

- iOS application.
- Separate learner-facing web application.
- Live AI voice conversations.
- Real-time video calling.
- Advanced 3D educational simulations.
- Multiplayer games and social feeds.
- User-generated public courses.
- Live tutoring or instructor marketplaces.
- Automated certification with professional accreditation.
- Complex AI recommendation models.
- Full offline access to the entire library.

These may be evaluated after validating the MVP.

# 7. Functional Requirements

Priority definitions:

- **P0:** Required for MVP launch.
- **P1:** Important, but may be deferred if budget or timeline is constrained.
- **P2:** Future release.

## 7.1 Authentication and Account Management

**Priority: P0**

### Requirements

- Users can register and sign in using supported authentication methods.
- Google sign-in may be offered.
- Email authentication may be offered.
- Phone OTP should only be included if budget, operational costs and product validation justify it.
- Users can sign out.
- Sessions must be securely managed.
- Users can request account deletion.
- Users can review privacy information.
- The application must handle authentication failures and expired sessions gracefully.

### Acceptance criteria

- A registered user can sign in and reach the Home screen.
- Invalid authentication attempts produce understandable errors.
- Session expiration does not cause an application crash.
- Signing out invalidates the local authenticated session.
- Account deletion initiates the documented deletion process and clearly explains any legally required retention.

**Priority: P0**

### Onboarding flow

1. Welcome screen.
2. Select primary learning goal.
3. Select current English proficiency.
4. Select explanation language.
5. Select daily learning goal.
6. Choose learning interests.
7. Create or sign in to an account.
8. Show a personalized Home screen.

### Learning goals

- Improve English.
- Prepare for interviews.
- Develop career skills.
- Improve confidence and communication.

### Proficiency levels

- Beginner.
- Elementary.
- Intermediate.
- Advanced.

These levels are for personalization and are not formal proficiency certifications.

### Daily goals

- 5 minutes.
- 10 minutes.
- 15 minutes.

### Acceptance criteria

- Onboarding preferences are saved to the user's profile.
- Users can change their preferences later.
- Users can skip nonessential questions.
- A first lesson is recommended based on the selected preferences.

**Priority: P0**

- The dashboard uses server-provided user and learning data.
- Empty states are shown for new users.
- Failed API requests do not leave indefinite loading indicators.
- The Continue Learning action opens the appropriate lesson.
- Premium content is clearly identified.

**Priority: P0**

### Initial learning paths

1. English Communication.

### Acceptance criteria

- Draft and unpublished courses are not visible to ordinary users.
- Course ordering follows admin-defined ordering.
- Access restrictions are enforced by the backend.
- Users can reopen completed lessons for revision.

## 7.5 Lesson Player

**Priority: P0**

The lesson player is the core learning experience.

### Supported content blocks

- Heading.
- Paragraph.
- Bullet list.
- Callout or key takeaway.
- Image.
- Audio.
- Video, where needed.
- Example conversation.
- Multiple-choice question.
- True/false question.
- Recap.
- Completion action.

The initial implementation should support structured lesson blocks rather than a fully customizable visual editor.

### Lesson screen requirements

- Display the lesson title and progress.
- Display estimated duration.
- Render the ordered content blocks.
- Support audio playback where available.
- Allow playback pause and resume.
- Allow the user to exit and continue later.
- Save progress at suitable checkpoints.
- Display a completion state.
- Offer a relevant next lesson.

### Acceptance criteria

- Lesson content is retrieved from the backend.
- Content is rendered in the configured order.
- Users can resume an unfinished lesson.
- Completed lessons remain available.
- Missing or unsupported content blocks fail gracefully.
- Audio controls provide accessible labels and clear playback states.

## 7.6 Quiz and Interactive Practice Engine

**Priority: P0**

### Initial question types

- Single-choice multiple choice.
- True or false.
- Scenario-based choice.
- Question with explanatory feedback.

### Example scenario

A learner is asked how to respond when an interviewer says, “Tell me about yourself.”

The application presents multiple response options and explains why one answer is more effective.

### Requirements

- Display one question at a time.
- Allow answer selection.
- Validate answers.
- Show correct or incorrect feedback.
- Explain the answer.
- Track quiz progress.
- Calculate the final score.
- Record attempts.
- Award eligible XP.
- Provide a review of mistakes.

### Scoring

For a quiz containing \(N\) questions, where \(C\) answers are correct:

\[
\text{Score} = \frac{C}{N}\times100
\]

The scoring model must handle an empty or invalid quiz safely.

### Acceptance criteria

- The same question cannot be counted twice within one completed attempt.
- Correct answers and explanations are returned from trusted server content.
- XP is not awarded repeatedly for duplicate completion requests.
- Quiz results can be reviewed after completion.
- The application can recover from temporary network interruptions without corrupting the attempt.

## 7.7 Audio Learning

**Priority: P0**

### Requirements

- Play audio associated with a lesson.
- Pause and resume playback.
- Display playback progress.
- Handle audio loading failures.
- Support Hindi or English narration where assets are available.
- Allow the user to mute or stop audio.
- Display text alongside audio where appropriate.

### MVP limitation

Audio will initially use pre-generated or manually uploaded recordings. Real-time conversational voice AI is excluded.

Text-to-speech may be used where voice quality, language support and licensing meet product requirements.

## 7.8 Progress Tracking

**Priority: P0**

### Track

- Lessons started.
- Lessons completed.
- Quiz attempts.
- Quiz scores.
- Learning minutes.
- Daily activity.
- Current streak.
- Longest streak.
- XP earned.
- Topic-level progress.

### Requirements

- Display progress in a simple dashboard.
- Display weekly activity.
- Allow users to revisit completed content.
- Calculate streaks using the configured day boundary and time zone.
- Handle repeated completion requests idempotently.
- Distinguish a lesson being opened from a lesson being completed.

### Completion rule

A lesson is completed when the user satisfies its configured completion criteria, such as reaching the end of the content and completing any required assessment.

Not every lesson must require a quiz.

## 7.9 Gamification

**Priority: P0**

### Experience points

Users earn XP for eligible learning activities.

Initial proposed rules:

| Activity | Proposed reward |
|---|---:|
| Complete an eligible lesson | 10 XP |
| Complete a quiz | 5 XP |
| Complete the daily challenge | 10 XP |
| Reach a daily learning goal | 5 XP |

These values are configurable. The backend must enforce the final reward rules.

### Streaks

- A streak increases when the user satisfies the daily learning condition.
- The condition should be based on meaningful completed activity, not simply opening the application.
- The daily boundary uses the configured time zone.
- The UI displays the current streak and progress toward the daily goal.

### Levels

The initial release may use simple XP thresholds for levels.

Level thresholds should be configurable, and the application must not reset accumulated XP when a new level is reached.

### Achievements

Initial achievements may include:

- First Lesson.
- First Quiz.
- Three-Day Streak.
- Seven-Day Streak.
- Ten Lessons Completed.
- Learning Goal Achieved.

### Acceptance criteria

- Rewards are calculated on the backend.
- Duplicate requests cannot repeatedly award the same completion reward.
- Users can view earned achievements.
- Streak calculations remain consistent across devices.
- Gamification does not expose private learning activity to other users.

## 7.10 Recommendations

**Priority: P0**

### Notification types

- Daily learning reminder.
- Incomplete lesson reminder.
- Streak reminder.
- Relevant new lesson announcement.

### Requirements

- Users can enable or disable reminders.
- Users can configure reminder preferences.
- Notification delivery must respect configured preferences.
- Notifications must not reveal sensitive personal information on the lock screen.
- Notification frequency must remain reasonable.

## 7.13 Premium Subscription

**Priority: P0 for a monetized launch**

### Proposed access model

Free users receive access to selected lessons and practice activities.

Premium users receive access to the premium course library and additional learning features.

### Proposed test pricing

- Monthly: ₹199–₹299.
- Annual: ₹1,499–₹1,999.

Prices are hypotheses to validate with users.

### Requirements

- Display the price, billing period and included benefits.
- Show renewal terms and cancellation information.
- Integrate Google Play Billing for eligible digital subscriptions sold through the Play-distributed app.
- Verify purchases using a secure backend process.
- Restore purchases where applicable.
- Handle expired, canceled, refunded and renewed subscriptions.
- Enforce premium access on the backend.
- Provide a clear subscription-management route.
- Do not assume a successful client-side purchase callback is sufficient proof of entitlement.

### Acceptance criteria

- A valid purchase grants the appropriate entitlement.
- An expired subscription no longer grants premium access, subject to applicable entitlement rules.
- A user can restore an eligible purchase.
- Billing failures display an understandable error.
- Free users cannot access premium content by bypassing client-side UI checks.

- Create and edit lessons.
- Add and reorder content blocks.

# 8. Content Strategy and Content Model

A proposed launch library:

- 3 learning paths.
- 6–10 courses.
- 50–100 reviewed lessons.
- 10–20 interactive communication scenarios.
- Short quizzes associated with appropriate lessons.

## 8.2 Content Standards

Every published lesson should have:

- A clear learning objective.
- An appropriate difficulty level.
- An estimated duration.
- Accurate and useful information.
- Clear, accessible language.
- Examples relevant to Indian users.
- A meaningful recap or practice activity.
- A defined free or premium access status.
- Editorial review and a content version.

## 8.3 Content Languages

The initial language strategy is English with optional Hindi/Hinglish explanations.

The data model should support additional languages without requiring changes to the core course structure.

Translations must preserve the meaning and educational intent of the original lesson.

## 8.4 Content Ownership

The business must have the necessary rights to all published text, images, illustrations, narration, music and video.

AI-assisted content should be reviewed for accuracy and suitability before publication.

- Lightweight UI transitions using Jetpack Compose.
- Lottie animations for achievements and feedback.
- Optional Rive animations for interactive illustrations.

## 9.2 Media Delivery

- Store media assets in object storage or an appropriate content delivery service.
- Store media references and metadata in the backend.
- Avoid embedding large videos directly in the Android application package.

## 9.3 Future Interactive Scenes

Interactive engineering and science simulations should be implemented as a separate capability.

Blender can produce rendered scenes and visual assets, but it does not by itself provide a complete Android runtime for interactive simulations.

# 11. Technical Architecture

**Technology:** Kotlin, Jetpack Compose, Material 3.

### Recommended architecture

- Presentation layer.
- Domain or use-case layer where useful.
- Data layer.
- Repository pattern.
- ViewModels.
- Coroutines and Flow.
- Retrofit or an equivalent HTTP client.
- Room for selected local persistence.
- DataStore for suitable local preferences.
- Secure token storage.
- A media playback component.

Avoid introducing unnecessary abstractions that slow development without improving maintainability.

**Technology:** NestJS and TypeScript.

# 13. Data and Business Rules

## 13.1 Lesson Completion

A lesson may be completed once its configured completion criteria are satisfied.

Repeated completion requests must not repeatedly grant the same completion reward.

## 13.2 XP Transactions

XP should be represented as auditable transactions.

The system should be able to determine:

- Why XP was awarded.
- Which activity generated it.
- When it was awarded.
- Whether the activity has already generated a reward.

Corrections to XP should be recorded through appropriate adjustment transactions rather than silently rewriting history.

## 13.3 Streak Calculation

- Define the user's daily activity boundary.
- Store timestamps consistently.
- Apply the configured time zone when calculating local days.
- Do not count merely opening the application as completed learning.
- Handle daylight-saving and time-zone changes safely.

## 13.4 Quiz Attempts

- A quiz attempt belongs to one user and one quiz.
- Answers must be associated with that attempt.
- The server calculates or verifies the final result.
- Duplicate submissions must not create duplicate rewards.
- The result should remain available for later review.

## 13.5 Subscription Entitlements

- The server is the authority for premium access.
- Purchase verification must not rely solely on client claims.
- Entitlement updates should be idempotent.
- Billing events should be processed safely when delivered more than once.
- Access changes should be reflected in a reasonable time.

# 14. Non-Functional Requirements

## 14.1 Performance

Proposed initial targets:

- Typical cached screen transitions should feel immediate.
- Under normal network conditions, common API responses should target a p95 latency below 500 ms, excluding large media downloads and third-party operations.
- Avoid unnecessary network calls during navigation.
- Paginate large content lists.
- Optimize images and audio.
- Avoid excessive animation on low-end devices.

These are engineering targets to validate through testing, not guarantees for every device or network.

## 14.2 Reliability

- Show understandable errors when network requests fail.
- Support retry for appropriate operations.
- Prevent duplicate rewards and duplicate billing entitlement updates.
- Preserve relevant local progress during short interruptions where feasible.
- Monitor production crashes and backend errors.

## 14.3 Security

- Use HTTPS.
- Validate input on the server.
- Apply authentication and authorization checks to protected routes.
- Rate-limit sensitive endpoints.
- Protect authentication tokens and secrets.
- Avoid logging passwords, tokens or sensitive personal data.
- Secure admin operations.
- Keep dependencies updated.
- Implement backup and restoration procedures.

## 14.4 Accessibility

- Support scalable text where practical.
- Maintain adequate contrast.
- Provide meaningful accessibility labels.
- Do not rely only on color to communicate correct or incorrect answers.
- Respect system accessibility settings.
- Provide text alongside important audio content.

## 14.5 Localization

- Support English content and Hindi/Hinglish explanations.
- Keep user-interface strings separate from application code.
- Store translations in a structured format.
- Design the content schema to support future languages.

## 14.6 Observability

Capture:

- Application crashes.
- API errors.
- Failed content loads.
- Quiz submission failures.
- Billing verification failures.
- Administrative publication events.
- Key product analytics events.

Logs must be designed with privacy and data minimization in mind.

# 15. Analytics and Success Metrics

## 15.1 North-Star Metric

**Weekly Active Learners Completing Meaningful Learning Activities**

Count distinct users who complete at least one eligible learning activity in a given week.

This is more meaningful than measuring application opens alone.

## 15.2 Activation Metrics

- Onboarding completion rate.
- Percentage of new users who start a lesson.
- Percentage of new users who complete their first lesson.
- Time to first lesson completion.

## 15.3 Engagement Metrics

- Daily and weekly active learners.
- Lessons completed per active user.
- Weekly learning minutes.
- Quiz completion rate.
- Daily goal completion rate.
- Day-1, day-7 and day-30 retention.

## 15.4 Learning Metrics

- Quiz score improvement across attempts.
- Lesson completion by category.
- Question-level error patterns.
- Review and revision activity.

Avoid treating time spent in the app as proof that learning has occurred.

## 15.5 Monetization Metrics

- Free-to-paid conversion.
- Trial conversion, if trials are offered.
- Monthly recurring revenue.
- Subscription renewal rate.
- Cancellation and refund rates.
- Revenue per paying user.
- AI and infrastructure cost per active user.

## 15.6 Initial Validation Targets

The following are proposed hypotheses for the first pilot, not industry benchmarks:

- At least 60% of users who start onboarding complete it.
- At least 40% of activated users complete a first lesson.
- Day-7 retention reaches 15–25% in the early cohort.
- Users report that the lessons are useful and appropriately localized.
- A measurable subset of engaged users expresses willingness to pay.

Collect baseline data before setting firm growth commitments.

## 16.1 Freemium Model

Free users should be able to experience meaningful learning value.

Premium benefits:

- Full course library.
- Additional interactive practice.

# 20. MVP Acceptance Checklist

The MVP is ready for launch when the following core journey works end-to-end:

1. A new user installs the Android application.
2. The user registers or signs in.
3. The user chooses a learning goal and language preference.
4. The Home screen recommends a relevant lesson.
5. The user opens a course and starts a lesson.
6. The lesson renders structured content correctly.
7. The user completes the lesson and takes a quiz.
8. The application displays the result and explanation.
9. Eligible learning activity updates progress and XP.
10. The Home and Progress screens reflect the updated data.
11. The user can return to the lesson and review content.
12. The admin can update and publish lessons without requiring an Android application release.
13. Premium content access is correctly enforced if subscriptions are enabled.
14. The user can manage preferences and request account deletion.
15. Production monitoring, backup and support procedures are in place.

# 21. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| Scope grows beyond the budget | Freeze MVP requirements and defer advanced AI and games |
| Content quality is inconsistent | Use a structured lesson template and editorial review |
| Users do not return | Test lesson length, practical value and reminder preferences |
| Subscription conversion is weak | Test pricing and improve free-to-premium value |
| Media production becomes expensive | Reuse characters, illustrations and animation templates |
| AI costs become unpredictable | Defer real-time AI and introduce usage controls later |
| Premium content is accessed without payment | Enforce entitlements on the backend |
| XP or streaks can be manipulated | Use server-authoritative rules and idempotent operations |
| Content is difficult to maintain | Make the admin panel part of the MVP |
| Poor connectivity harms learning | Optimize media, cache appropriate content and provide useful retry states |

# 22. Future Product Opportunities

After the MVP demonstrates engagement and willingness to pay, evaluate:

### AI Learning Coach

Explain lesson concepts, answer questions and generate additional practice with controlled, reviewed prompts.

### AI Speaking Practice

Support voice-based role-play, spoken-English practice and interview simulations. Evaluate speech recognition quality, latency, privacy and per-user costs.

### Blender-Based Educational Animations

Create reusable 3D scenes for science, finance and practical problem-solving lessons. Use rendered video for explainer content and real-time rendering only where interaction warrants it.

### Interactive Storytelling

Create branching conversations for interviews, workplace situations and customer interactions. Store story scenes and choices as structured content so the admin team can update them.

### Additional Languages

Add further Indian languages based on actual usage and demand rather than attempting every language at launch.

### B2B Learning

Explore college, employer and training-institute licensing once the individual learner experience is validated.

# 23. Final Product Recommendation

The first version should not attempt to reproduce every feature of SmartyMe.

It should deliver one complete, polished learning experience:

**Discover a lesson → learn a concept → practice → receive feedback → earn progress → return for the next lesson.**

The strongest starting proposition is English communication and career development for Indian learners, supported by Hindi/Hinglish explanations and practical scenarios.

Build the content management foundation early, keep the Android architecture modular, use gamification carefully, and introduce advanced animation and AI only when they improve learning outcomes or retention.

**Recommended next milestone:** approve the MVP scope and produce the detailed screen-by-screen UX specification, database model, API contracts and module-wise implementation backlog before starting development.
